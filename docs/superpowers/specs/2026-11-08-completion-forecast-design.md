# 完了見込み: 進捗(残りの工数)に対応した今日からの完了日(要望 133)設計書

> 日付: 2026-11-08 / ブランチ: `feature/completion-forecast` / 関連: 要望 132(遅延対応。`crew_trial.py`)・103(警告)・98(残りの工数)

## 1. 目的と範囲

アプリの完了予定(`effective_end`)は、開始日から**全工数**を担当で消化して算出し、進捗度を見ない。そのため、
- 遅れたタスクの完了予定は過去のまま残り、増員を確定しても変わらない(要望 132 の確定後に、完了予定・警告が動かない)。
- 進捗が進んでいても、遅れていても、完了予定の日付は同じ。

進捗を見た「**完了見込み**」(今日からの残りの工数を、今の担当で消化して終わる日)を、**別の概念として足す**。

守ること:
- **当初の完了予定は変えない**。予定超過(`完了予定 ≤ 今`)・警告の判定式・先行の押し出し・PlantUML・CSV・担当者向けファイルは今のまま。完了予定を置き換えると、予定超過が永久に判定されなくなる。
- ファイル形式は変えない(`version` は 21 のまま。見込みは保存せず、表示のたびに算出する)。
- 要望 132 の試算と確定後の見込みを、同じ計算(`forecast_end`)にする。

範囲外: 見込みを先行の押し出しや後続の開始に使うこと、見込みの色の設定画面、警告の判定式の変更。

## 2. 計算: `forecast.py`(新規。純粋関数。NiceGUI に依存しない)

```python
@dataclass(frozen=True)
class Forecast:
    end: datetime            # 完了見込み
    planned_end: datetime | None  # 当初の完了予定(effective_end)

    @property
    def days_later(self) -> int | None:  # 見込み − 当初の予定の日数(早ければ負)

def forecast_end(task, project, holidays, now, schedule, extra_crew=None) -> Forecast | None
```

- **対象**: 通常タスクで、終了していない(`status` が `終了` でない)もの。残りの工数(`remaining.remaining_hours`)が 0 より大きいもの。実効の開始が今日以前のもの。それ以外は `None`(開始が未来のタスクは、見込み = 当初の予定なので出さない)。
- **起点**: `max(今日, 実効の開始)`。
- **工数**: `remaining_hours`(工数 − 消化分。進捗度があれば工数 × 進捗度、なければ実績の区間 × 換算率。状態は手入力なので、未着手でも進捗度か実績があれば引く)。
- **担当**: 今日の担当(`crew_on`)。週ごとのタスクは、週の区切りを**実効の開始から 7 日ごと**に数えたまま使う。このため `timeline.calc_end` に `weeks_start: date | None = None` を足す(`work_capacity` に前例がある。既定の `None` は従来どおり `start` から数える)。
- **`extra_crew`**: 試算用の増員(`TrialCrew` 相当。名前の列と開始日)。増員日は、今日から数えた週の境目に、**遅い側**へ丸める(今日以前は今日から)。
- 手動指定の完了予定のタスクも、見込みは出す(手動指定は当初の約束で、見込みは別の情報)。
- 日付が範囲を超える・稼働日がない等で算出できないときは `None`。例外にしない。

**要望 132 との共通化**: `crew_trial.evaluate` の `from_now`(遅れ・警告のタスク)の枝を `forecast_end(extra_crew=…)` の呼び出しに置き換える。試算の `baseline_end` は `forecast_end` を `extra_crew=None` で呼んだ値。確定後は、同じ `forecast_end` が、確定した `weekly_crew` で見込みを出す(試算の見込みと一致する。確定の増員は次の週の境目なので、増員日が今日と同じ週のときは、試算より遅く出ることがある)。

## 3. 表示

- **ガントチャートの棒**: 見込みの**日付**が当初の完了予定の日付と違うときだけ、棒の完了予定の位置から見込みの位置まで細い灰青の点線を伸ばし、右に `見込み m/d(+N 日)` を出す(早まるときは `−N 日`)。色は、赤(遅れ)・黄(警告)・緑(取り戻せた)・紫(遅延対応の試算)とは別系統の灰青(`--forecast`)。ライト・ダークの値を持つ。
  - 遅延対応の試算中のタスクは、試算の表示を優先し、見込みは出さない。
  - 表示オプション `show_alerts` に従う。
  - 終了済み・開始が未来・残り 0 のタスクには出さない(`forecast_end` が `None`)。
- **下部パネルの詳細**: `完了予定 m/d` の下に、`完了見込み m/d(+N 日)` を 1 行出す(見込みがあるときだけ)。
- **ダッシュボード**: `進捗と遅れ` の遅れの一覧の各行に、見込みの日付(`見込み m/d`)を並べる。
- **警告**: 判定の式は変えない。ホバーに `完了見込み m/d` を足す。警告のタスクは、必ず `見込み > 当初の完了予定`(同日を含まない)になる。この性質をテストで保証する(`警告 = 残り ÷ 稼働量 ≥ 1.10`、見込みは稼働量で消化するので、残りが稼働量を超えれば必ず後になる)。

見込みの計算は、描画ごとにタスクあたり 1 回だけ(`GanttChart` が描画の間、結果を使い回す)。

## 4. ファイルの分け方

- `forecast.py`(新規): `Forecast`・`forecast_end`。
- `timeline.py`: `calc_end`・内部の `_calc_end`・`_crews` 周りに `weeks_start` を通す。
- `crew_trial.py`: `from_now` の枝を `forecast_end` に置き換える。`TrialResult` の形・`days_earlier` の意味は変えない。
- `gantt.py`: 見込みの点線と文言。`bottom_info.py`: 詳細の行。`dashboard.py`・`dashboard_view.py`: 遅れの一覧の見込み。`pace.py`: 警告のホバー。`delay_response.py` か新しい CSS: `--forecast` の色。

## 5. テスト

1. 純粋関数: 進捗なしの見込みが当初の予定と一致する(開始が今日以前で、まだ遅れていないとき)。進捗ありで早まる。遅れたタスクは今日起点になる。週ごとの担当は、週の区切りが開始から数えたまま。終了済み・残り 0・開始が未来・担当なし(換算率 1)・算出できない値は、落ちずに期待どおり(`None` または既定)。手動指定の完了予定でも見込みが出る。
2. `calc_end` の `weeks_start` を省略したとき、従来と完全に同じ結果になる(既存のテストが通る)。
3. 警告のタスクは、必ず `見込み > 当初の完了予定`。
4. 要望 132: 共通化の前後で、試算の数字(`trial_end`・`baseline_end`)が一致する。確定後の見込みが、増員日が次の週の境目より先のときに、試算の見込みと一致する。
5. 画面: 棒の点線と文言、詳細の行、遅れの一覧、隠す条件(試算中・終了済み・日付が同じ・`show_alerts` オフ)。
6. 性能: 300 タスクで、見込みの追加が 0.1 秒未満。

## 7. 未決・限界

- 見込みは、残りの工数を今の担当が並行して進める前提の算術で、予測ではない(立ち上がりの遅れ・休みの予定外の変更は見ない)。
- 先行のタスクが遅れていても、後続の見込みには反映しない(押し出しは当初の予定のまま)。必要なら別の要望にする。
- 進捗度が未入力で実績もないタスクは、全工数が残りとして数えられる(開始が今日以前なら、今日からの見込みになる)。
