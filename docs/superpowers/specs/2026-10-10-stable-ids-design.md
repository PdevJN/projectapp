# メンバーとセクションの安定 id(ファイル形式 v2)設計書

2026-10-10。architectural。ブランチ `feature/stable-ids`。

## 背景と目的

プロジェクトファイルの構造のレビュー(2026-10-10)で、同一性の持ち方が弱いと指摘した。安定した id があるのはタスクだけで、メンバーは名前、セクションは位置(`SectionPath`)で識別している。担当者向けの書き出し(`handoff.py`)の id や、後続の外部インポート(要望 5)の突き合わせには、改名や並べ替えで変わらない識別子が要る。

目的は、**ファイルの中の識別子を安定させる**こと。実行時のモデルの参照(担当者を名前で引く約 30 箇所)は変えない(決定: ファイルだけ id にする)。

## 決定事項

- `Member` と `Section` に `id` を付ける。`new_id()` の 8 桁の 16 進(`Task.id` と同じ)。`compare=False`(比較に使わない)。
- ファイルでは、担当者がメンバーの `id` を指す。実行時の `Assignee` は `name` のまま変えない。
- `FORMAT_VERSION` を 2 に上げる。

## ファイル形式(version 2)

```
members:  [{"id", "name", "ratio", "levels"}]
sections: [{"id", "name", "tasks", "sections"}]
tasks[].assignees: [{"member": "<メンバーid>", "allocation": 1.0}]
```

- `Assignee.name` は、ファイルには書かない。保存は `asdict` の結果のうち、担当者だけを「名前 → メンバー id」に置き換える(`storage` の局所的な変換。シリアライズ層の統合は範囲外)。
- 読込は、メンバー id から名前へ戻して `Assignee(name, allocation)` を作る。

## 読込のルール

version 1(キーなしを含む):

- メンバーとセクションに、新しく id を振る(保存し直すと残る)。
- 担当者は、今までどおり名前(`assignees[].name`、または旧キー `assignee`)で読む。一覧にない名前はメンバーとして補う(今の挙動)。
- 保存すると version 2 になる。

version 2:

- メンバーとセクションの `id` は、キーなし・`null`・空・文字列以外・重複(メンバー同士、セクション同士。別種の間は問わない)を拒否する。
- 担当者の `member` は、文字列で、メンバーに存在する id でなければ拒否する。担当者に旧キー `name` があっても拒否する。割り当て率の検証と、同じメンバーが 1 タスクに 2 回の拒否は、今までどおり。
- メンバー名の空・重複は、今までどおり最初の 1 件を残して捨てる(読込時)。捨てられた重複メンバーの id を担当者が指していても拒否せず、残った同名のメンバーへ読む。
- チェックポイントの担当は空にする(今まで通り)。

## 画面側の変更

- **メンバーのダイアログ**: `build_members` は行ごとに `Member` を新しく作るので、何もしないと保存のたびに id が変わる。`MemberRow` に `id` を持たせ(新しい行は `None`)、`build_members` が既存の id を引き継ぎ、新しい行にだけ `new_id()` を振る。改名しても id は変わらない。
- **セクションの追加**(`views.py` のトップとサブ): `Section(name)` が自動で `new_id()` を振る(変更なし)。
- **行のコピー**(`arrange.py`): タスクは新しい id、セクションはコピーしない(変更なし)。
- 画面の見た目・操作は変わらない。

## 範囲外

- 実行時の id 化(`Assignee.member_id` など)。
- `handoff.py` の id の見直し(今は `uuid5`(プロジェクト名・タスク名))。要望 5 で扱う。
- パラメータ・段階・URL テンプレートの id。
- 保存と読込のシリアライズ層の統合(提案 3)。
- セクションの改名・削除・移動(今もできない)。

## ドキュメント

`docs/development.md` の「ファイル形式の注意」に、version 2 の形式と、version 1 の読込を追記する。`CLAUDE.md` の `version` の記述を 2 に直す。

## テスト

- version 1 の読込で、メンバーとセクションに id が振られ、担当者が名前で読める(旧キー `assignee` を含む)。
- 保存したファイルに `version: 2`、メンバーとセクションの `id`、担当者の `member` が入り、`name` は入らない。
- 保存 → 読込 → 保存で、id が変わらない。
- version 2 の不正を拒否する: `id` の欠落・空・重複(メンバー、セクション、入れ子のセクション)、存在しない `member`、旧キー `name`、`member` が文字列でない。
- 重複メンバーを捨てたとき、担当者は残ったメンバーへ読まれる。
- メンバーのダイアログ: 改名しても id が保たれる、新しい行に新しい id が振られる、削除した行の id は残らない。
- 既存のテストデータ(version 1)が引き続き読める。
- 全体のテストと `ty` が通る。

## リスクと注意

- 新しいアプリが書いた version 2 を、この変更より前のアプリ(version 1 までしか知らない)で開くと、担当者が失われる。`version` の検査は今日から入ったので、これ以降のアプリは拒否する。この変更より前のアプリは検査がないので、新しい形式のファイルを共有するときは注意が要る(個人利用で許容)。
- id は 32 ビットなので衝突の可能性はあるが、読込で重複を拒否する。生成時に重複を確かめる処理(メンバー・セクション・タスクを通じた一意化)は、今回は入れない。
