# タスク編集ダイアログの見直し 設計書

## 目的

タスクの追加・編集ダイアログ(`forms.open_task_dialog`)を、次の6点で使いやすくする。ブランチは `feature/task-edit-dialog`。

| # | 項目 | 状態 |
|---|---|---|
| 1 | 優先度を色付きチップで選ぶ | 実装済み(実機の確認待ち) |
| 2 | タスクを削除できるようにする | 未着手 |
| 3 | 開始・終了を、日付を選ぶ方式にする(時刻はチェックボックスで追加できる。時刻なしは、開始=始業時刻、終了=始業+8h+昼休憩1h) | 未着手 |
| 4 | 開始と終了を横並びにする | 未着手 |
| 5 | 色のプレビューを表示する | 未着手 |
| 6 | ダイアログを閉じるとき、編集内容を確定するか確認する | 未着手 |

## 範囲

**含む**: 上の6点、それに伴うダイアログの幅の変更、`views.py` の削除処理、テスト。

**含まない**:
- データ形式の変更(`Task.start` / `Task.end` は `datetime` のまま。保存形式も変えない)
- 「状態」の選択方法の見直し
- 一覧・ガントへの優先度の表示
- 他のタスクからの連結(`predecessors`)の整理(連結はまだ画面にない。実装するときに、削除との関係を決める)
- セクションの編集・削除、タスクの並べ替え

## 決定事項

下の A〜E は、こちらで置いた初期案。違えば直す。

- **A. 時刻を指定しないときの時刻**(利用者の指定):
  - **開始**は、プロジェクトの始業時刻(`Project.work_start`。稼働設定)で補う。
  - **終了**は、始業時刻 + 標準稼働時間 `8:00` + 昼休憩 `1:00` で補う。始業が `09:00` なら `18:00`。
  - 標準稼働時間(8h)と昼休憩(1h)は、**固定の定数**(`STANDARD_WORK_HOURS`、`LUNCH_HOURS`)で、プロジェクトの設定ではない。昼休憩の設定は稼働時間の設定の対象外(`2026-10-03-work-hours-design.md`)のままにする。
  - 終了日だけを選べば、その日の終業の時刻(通常は 18:00)で終わるので、**終了日の当日がバーに含まれる**。
  - 始業が遅く、始業 + 9h が24時以上になるとき(始業が15:00以降)の扱いは、**保留事項**(下の「保留事項」)。このブランチでは、暫定の安全策として、補う終了を `23:59` で頭打ちにするだけにする(1行。24:00 は表せないため)。
  - **日程計算の稼働枠(始業から `daily_hours` の連続した枠。昼休憩なし)とは別の概念**。工数から自動算出された終了(例: 9:00 + 6.5h = 15:30)は、この補う終了(18:00)と一致しない。補う終了は、利用者が日付だけを選んだときの入力補助にだけ使う。
- **B. 時刻のチェックボックスは1つ**: 「時刻も指定する」を1つだけ置き、チェックすると開始・終了の両方に時刻入力が出る。開始と終了を別々にする必要は、いまはない(YAGNI)。
- **C. 削除は確認つき**: 削除ボタンを押すと、「『名前』を削除しますか?」の確認ダイアログを出す。取り消しの手段(元に戻す)はまだないため。
- **D. 閉じる確認は、変更があるときだけ**: 開いた直後から何も変えていなければ、確認なしですぐ閉じる。
- **E. ダイアログの部品を `task_dialog.py` に切り出す**: `forms.py` は 340 行近くになり、ダイアログが大きく変わるため。検証(`build_task`、`parse_datetime` ほか)は `forms.py` に残し、`open_task_dialog`、`PriorityChips`、日付・時刻の入力部品を移す。`views.py` と既存テストの import を直す。

## 画面

幅を `w-96` から広げ、開始と終了を並べる。

```
タスクの編集
名前          [__________________________]
開始                      終了
[2026-10-05 📅]           [2026-10-07 📅]
[09:00 🕘]  ← 時刻を指定したときだけ表示
☐ 時刻も指定する
工数(時間)    [____]
優先度        [高] [中] [低]     ← チップ
状態          [開始      ▼]
色            [#4c8bf5 🎨]       ← ボタンが選んだ色になる
担当者        [__________________________]

[削除]                [キャンセル] [保存]
```

- **日付の入力**: 日付のテキスト入力(`YYYY-MM-DD`)と、右端のカレンダーアイコンで開く日付選択ダイアログ(`ui.date`)。稼働時間の設定の時刻選択(`open_settings_dialog`)と同じ方式にする。ネイティブの `type=date` は、小さなウィンドウでポップアップが切れたため使わない。
- **時刻の入力**: 「時刻も指定する」をチェックすると、各日付の下に `HH:MM` の入力と、時計アイコンの時刻選択ダイアログが出る。
- **開いたときのチェックボックスの初期値**: 新規は未チェック。編集では、既存の開始が始業時刻と違うか、終了が補う終了時刻と違えばチェック済み、どちらも同じ(または空)なら未チェックにする。自動算出の終了(例: `15:30`)は、補う終了と違うので、チェック済みで開く。
- **削除ボタン**: 編集のときだけ表示する(新規では出さない)。左端に、赤の文字のフラットボタンで置く。
- **色のプレビュー**: `ui.color_input` の `preview=True` で、色の選択ボタンが選んだ色になる。
- **優先度**: 実装済みの `PriorityChips`。

## 日付・時刻の扱い(項目 3)

ダイアログは、日付と時刻から `YYYY-MM-DDTHH:MM` の文字列を組み立て、いまの `build_task` にそのまま渡す。`build_task` の検証と、自動算出の終了の判定(`end_unchanged` など。分単位の比較)は変えない。

- 日付が空なら、開始・終了とも空(`None`)。時刻が入っていても無視する。
- 日付が入っていて時刻が空(時刻の指定あり)のときは、補う時刻を使わず、「時刻の形式が正しくありません」とする。
- 時刻のチェックを外すと、時刻の入力は補う時刻に戻して隠す。
- **補う時刻を決めるため、`open_task_dialog` が `work_start` を受け取る**。`views.py` が `project.work_start` を渡す。`daily_hours` は受け取らない(終了は定数から決まる)。補う開始・終了の時刻は、`default_times(work_start) -> tuple[time, time]` の純粋関数にする。
- 稼働時間の設定で始業時刻を変えると、補う時刻も変わる。開き直したときのチェックボックスの初期値と、組み立てる文字列は、そのときの始業時刻から決める。すでに保存済みのタスクは、開始・終了とも値そのものが残るので、設定変更で動かない(自動算出の終了は従来どおり `recalc_ends` が更新する)。

## 編集を閉じるときの確認(項目 6)

- ダイアログを `persistent`(背景のクリックと `ESC` で、勝手に閉じない)にして、閉じる操作を自前で扱う。
- 閉じる操作(「キャンセル」ボタン、`ESC`)で、**変更があるときだけ**確認ダイアログを出す。ボタンは次の3つ。

| ボタン | 動作 |
|---|---|
| 保存(確定) | 「保存」ボタンと同じ。検証に失敗したら、編集ダイアログに戻ってエラーを表示する |
| 破棄して閉じる | 保存せずに閉じる |
| 編集に戻る | 確認だけ閉じて、編集を続ける |

- **変更の判定**: 開いた時点の入力値(名前、日付、時刻、時刻のチェック、工数、優先度、状態、色、担当者)の組を覚えておき、いまの組と比べる。`asdict` との比較は使わない(ここではまだタスクが作られていないため)。
- 変更がなければ、確認なしですぐ閉じる(D)。
- 背景のクリックは、`persistent` では閉じず、揺れる(`shake`)だけにする。確認は出さない。これは実装時に、Quasar の挙動を実機で確かめる。`ESC` を拾えない場合は、「キャンセル」ボタンだけを確認の対象にして、設計書を直す。

## タスクの削除(項目 2)

- `open_task_dialog(task, on_save, on_delete=None)`。`on_delete` があるときだけ、削除ボタンを出す。
- 削除ボタン → 確認ダイアログ(C)→「削除」で `on_delete()` を呼び、確認と編集ダイアログの両方を閉じる。変更の確認(項目 6)は経由しない(削除すれば入力は不要になる)。
- `views.MainView.delete_task(section_index, task_index)`: 該当するタスクを `tasks_in(...)` から取り除いて、`gantt.set_project` で再描画する。`edit_task` が `on_delete` を渡す。
- 保存は自動では行わない。削除は「編集中」の判定に入る(`asdict(project)` と `snapshot` の差)。
- 他のタスクの `predecessors` は、画面で設定する機能がまだないので、触らない。

## テスト

- `default_times`: 始業 09:00 → (09:00, 18:00)、始業 08:30 → (08:30, 17:30)。始業 17:00 の暫定の頭打ち(終了が 23:59)を1件だけ確かめる(保留事項の対応で置き換わる)。
- 日付・時刻の組み立て(純粋関数に切り出す): 時刻なしで補う時刻が入る/時刻ありはそのまま/日付が空なら空/形式不正でエラー。
- チェックボックスの初期値の判定: 開始・終了が補う時刻と同じか空なら未チェック、どちらかが違えばチェック済み(自動算出の終了を含む)。
- 日付だけで保存した開始が始業時刻、終了が 18:00 で入る(始業 09:00 のとき)。始業を変えたプロジェクトでは、それに追従する。時刻を指定して保存すると、その時刻になる。
- 既存の「自動算出の終了」のテストが、日付・時刻の入力でも通る(`end_auto` が保たれる/外れる)。
- 優先度チップ(実装済み)、「状態」の幅(実装済み)。
- 色: `preview` が有効になっている。
- 閉じる確認: 変更なしで閉じる→確認が出ない。変更ありで閉じる→確認が出て、「保存」で保存される、「破棄」で保存されない、「編集に戻る」でダイアログが残る。保存で検証に失敗すると、編集ダイアログにエラーが出て閉じない。
- 削除: 新規には削除ボタンがない。削除→確認で「キャンセル」なら残る。「削除」でタスクが消えて再描画される。セクション内のタスクと、セクションなしのタスクの両方。削除後は編集中になる。
- 実機で確認する項目(自動テストでは見えない): 開始・終了の横並び、日付選択ダイアログが小さなウィンドウで切れないこと、色のプレビュー、チップの色(ライト/ダーク)、`ESC` と背景クリックの挙動。

## 実装の順序

1. 優先度チップ(実装済み)をコミットする。
2. 色のプレビュー(`preview=True` のみ)。
3. `task_dialog.py` への切り出し(E。動作は変えない)。
4. 日付・時刻の入力(A・B)と、開始・終了の横並び。
5. 閉じるときの確認。
6. 削除。

各項目の完了ごとに、テストと `ty check` を通してからコミットする。

## 先送りした点

- 時刻の入力を、開始・終了で別々にチェックできるようにすること(B)。
- 日付が過去の日付や基準日より前のときの警告。
- 削除の取り消し(元に戻す)。

## 保留事項(別ブランチで扱う)

### 始業が15:00以降のときの補う終了

補う終了(始業 + 8h + 昼休憩 1h = 始業 + 9h)は、始業が **15:00以降**だと24時以上になる(15:00 でちょうど 24:00 で、表せない)。このブランチでは暫定の頭打ち(`23:59`)だけを入れ、本来の対応は、別ブランチ(例: `feature/work-start-limit`)で扱う。

### 稼働設定のオプション「始業時刻を制限する」(案)

上の問題を、補う側ではなく**設定側で防ぐ**案。稼働時間の設定ダイアログ(`open_settings_dialog`)に、オプションのチェックボックスを置く。

- 名前(仮): 「始業時刻を15:00より前に制限する」。**既定はオフ**(いまの動作のまま)。
- 保存先: `Project` のフィールド(例: `limit_work_start: bool = False`)。古いファイルは、フィールドがなければオフとして読む。

**オプションをオンにしたときの制限事項**(実装時に、そのまま仕様とテストにする):

1. **始業時刻は `00:00`〜`14:59` だけ**。`15:00` 以降は設定できない(15:00 自体も不可。補う終了が 24:00 になるため)。入力中に警告し、「適用」でも拒否する(稼働可能時間の範囲の扱いと同じ)。
2. **既存の「始業 + 稼働可能時間 ≤ 24:00」の検証も、そのまま有効**(両方を満たす必要がある)。
3. **始業が15:00以降のプロジェクトでは、オプションをオンにできない**。先に始業を14:59以前に直す(同じ「適用」で両方を変える場合は、新しい始業で判定する)。
4. **オンにしても、保存済みのタスクは変わらない**。始業時刻の設定そのものを制限するだけで、タスク編集ダイアログで入れる時刻や、手入力・自動算出の終了には、制限をかけない。
5. **オフに戻せる**。オフに戻すと、始業時刻の制限は外れる(既存の始業の値は変わらない)。
6. **プロジェクトごとの設定**で、他のプロジェクトには影響しない。
7. オンのときは、補う終了(始業 + 9h)が必ず 24:00 より前になる。そのため、暫定の頭打ち(`23:59`)は、オンのプロジェクトでは働かない。オフのプロジェクトでは、暫定の頭打ちか、別ブランチで決める対応が、働く。

**未決(別ブランチで決める)**:
- オフのときの本来の対応(頭打ちを残す、翌日にまたぐ、補わずに時刻の入力を必須にする、など)。
- 昼休憩を固定の 1h にせず、設定にするか。
