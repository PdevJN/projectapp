# 相対比率の加算分の上限・下限の設計(要望 73)

> **状態**: 実装済み・実機確認済み・`develop`へマージ済み(2026-10-28。PR #108)— 要望 73・75 — `feature/ratio-limits`(削除済み)。現在の仕様は [`CLAUDE.md`](../../../CLAUDE.md) に反映済み。計画は `docs/superpowers/plans/2026-10-28-ratio-limits.md`。

> **改訂(2026-10-28。要望 75)**: 制限の対象を、加算分(判定値の合計)から**相対比率そのもの**に置き換えた。以下の本文は当初の設計(加算分の制限)で、次の点が変わっている。
> - 計算: `ratio = min(max(基本比率 + 判定値の合計, 下限), 上限)`。空欄の側は既定の 50〜150%。基本比率だけのメンバーにも掛かる(基本 200% は上限 150% で 150%)。
> - 入力と範囲: 下限・上限はどちらも 50〜150% で、下限 ≤ 上限(読込・設定ダイアログで検証)。プリセットは `50% 〜 150%`。
> - 注記: `相対比率 250% → 上限 150% に制限`。`RatioDetail.adjustment` と `ratios.limit_adjustment` は廃止。
> - 保存のキー(`ratio_limit_upper`・`ratio_limit_lower`)と version 13、3 者マージ、見直し確認(`reassign.limit_reviews`)は変わらない。
> - 既定の丸め範囲も 10〜300% から **50〜150%** に変えた(`DEFAULT_RATIO_MIN`・`DEFAULT_RATIO_MAX`)。設定の下限・上限は、この範囲の中で狭められ(入力・読込とも 50〜150%)、基本比率の入力・読込の範囲は 10〜300% のまま。結果が変わることの通知は出さない。
> - 見直し確認をキャンセル・外側クリック・ESC で閉じたときは、「上限・下限は変更しませんでした」と通知する。

## 目的

相対比率は`基本比率 + 判定値の合計`で決まる。パラメータが増えるほど合計が大きく(または小さく)なり、実態より過大な消化速度(過小な見積もり)になりやすい。例えば基本 100% の人が、複数のパラメータで 150% を超えると、過大に見える。ゴールは、パラメータによる加算分に上限・下限を設けて、この乖離を抑えること。成功の目安は次のとおり。

- 上限 +50%・下限 -50% を設定したプロジェクトで、基本 100% の人は 50〜150% の範囲に収まる。基本 200% の人は 150〜250% で、基本比率より極端に下がらない。
- 上限・下限が未設定(既定)のプロジェクトは、完了予定・換算率・負荷・見積もりが今までと変わらない。
- 完了予定・ダイアログの換算率・担当者向けファイルの見積もり・担当付け替え時の見直しが、同じ制限後の値を使う。

## 決めたこと(2026-10-28 に確認済み)

| 項目 | 決定 |
| --- | --- |
| 方式 | 足しこみのまま。加算分(判定値の合計)に上限・下限を設ける。乗算・平均・逓減の方式は入れない |
| 制限の対象 | 加算分。相対比率そのものではない(基本比率が高い人を、基本より下げないため) |
| 上限・下限 | 別々の欄。空欄は制限なし(既定)。要望の運用値は上限 +50%・下限 -50% |
| 範囲 | 上限は 0〜+290%、下限は -90〜0%(判定値の範囲と同じ)。上限 < 下限にはならない |
| 丸め | 今と同じ(10〜300%)。制限のあとに適用する |
| 付けたパラメータ | タスクに付けたパラメータだけを数える場合(要望 51)も、その合計に制限をかける |
| 置き場所 | プロジェクトの設定(プロジェクトごと)。全プロジェクト共通にはしない |
| 判定値の範囲 | 変えない(-90〜+290%) |

## 課題への対応

| 課題 | 対応 |
| --- | --- |
| 正と負が混ざったときの割り引き(逓減) | 逓減を入れない。合計に対する制限なので、打ち消し合う要因は割り引かれない |
| 平均の分母 | 平均を入れない |
| 重みの根拠がない | 重みを使わない。上限・下限は利用者が決める値 |
| 制限を変えたときの完了予定のずれ | 保存前に確認を出す(下の「設定ダイアログ」) |
| 丸めで乖離が見えにくい | 制限したときは、内訳に出す(下の「内訳」) |

## データ(`models.py`・`storage.py`・`merge.py`)

- `Project.ratio_limit_upper: float | None`・`Project.ratio_limit_lower: float | None`(既定はどちらも `None`。割合の小数で、判定値と同じ単位。例: +50% は 0.5)。
- 保存は、プロジェクト直下の `ratio_limit_upper` / `ratio_limit_lower`(数値か `null`)。`FORMAT_VERSION` を 12 から 13 に上げる。キーのない古いファイルは `None` として読み(移行は要らない)、数値でない・非有限・範囲外(上限 0〜+2.9、下限 -0.9〜0)は読込を拒否する。値は小数点以下 4 桁に丸める(判定値と同じ)。
- 3 者マージ: プロジェクトの設定として、2 つの値をそれぞれ 1 項目として比べる(`SETTING_LABELS` に`相対比率の上限`・`相対比率の下限`を足す。`reference_mode`・`plantuml_overload_notice` と同じ扱い)。

## 計算(`ratios.py`)

- `ratio_detail(member, parameters, only=None, limits=None)` と `effective_ratio(...)` に、`limits: RatioLimits | None` を足す。`RatioLimits` は `upper` と `lower`(どちらも `float | None`)を持つ凍結データクラス。
- 加算分 `adjustment = Σ判定値`(`only` があれば付けた分だけ)を、`[lower, upper]` に収める(`None` の側は収めない)。`raw = round(base + 収めた加算分, 4)`、`ratio = min(max(raw, MIN_RATIO), MAX_RATIO)` は今と同じ。
- `RatioDetail` に、収める前の加算分 `adjustment` と、収めたかどうか `limited: bool`(上限か下限で収めた)を足す。`clamped`(10〜300% への丸め)は今のまま。
- `crew_of`・`assignees_rate`・`conversion_rate(task, project)` などの呼び出し側は、`project` から `RatioLimits` を作って渡す。`timeline.py`・`task_dialog.py`・`forms.py` の呼び出し箇所を、同じ限りで揃える。

## 設定ダイアログ(`forms.py`・`views.py`)

- プロジェクトの設定に、`相対比率の加算分の制限`の節を足す。`上限`・`下限`の 2 つの欄(%。空欄は制限なし)と、`+50% / -50% を入れる`のプリセットのボタンを置く。範囲外・数値でない入力は欄にエラーを出し、適用を押せなくする。
- 適用は、稼働可能時間の変更と同じく、完了予定へすぐ反映する。元に戻す・やり直しの対象にする。
- 制限を変えて、換算率が変わるタスクのうち、通常タスクで、工数があり、状態が`終了`でなく、実績か進捗度(1% 以上)があるものがあるときは、適用の前に、その件数を出す確認を挟む(要望 32 と同じ条件)。選択肢は`見直して適用`・`見直さずに適用`・`キャンセル`。`見直して適用`は、要望 32 の見直しと同じ規則(完了予定を`max(今, 開始予定)`から`(工数 − 消化分) ÷ 新しい換算率`で再算定し、手で指定の完了予定として保存する)を、該当するタスクすべてに適用する。そうでないときは確認を出さない。

## 内訳の表示(`forms.py`・`task_dialog.py`)

- 制限したときだけ、換算率の内訳に`加算分 +80% → 上限 +50% に制限`のように添える(下限も同様)。制限しなかったときは今の表示のまま。
- メンバーの画面の`effective_ratio_text`も同じ。10〜300% への丸めの表示は今のまま。

## 周辺の挙動

- 割り当て超過・ダッシュボードの負荷と予定工数は、割り当て率で数えて相対比率を使わないので、変更しない。担当者向けファイルの見積もり・週ごとの担当の完了予定は、相対比率を `ratios.py` 経由で求めるので、追加の変更は要らない。実装計画の最初に、`ratio_detail` / `effective_ratio` を通らずに判定値を足している箇所がないかを、全体で再確認する。
- PlantUML と担当者向けファイルには、独自のキーを足さない。
- プロジェクト参照のスナップショットは、値(日程・負荷)を保存するため、制限を変えても参照先の値は、取り直すまで変わらない(既存の仕様どおり)。
- PlantUML の取り込み・CSV の取り込みは、制限なしで作る。

## テスト

- `ratios`: 上限だけ・下限だけ・両方・制限なし(従来と同じ結果)。境界の値(ちょうど上限・下限)。`only` で付けたパラメータだけを数える場合。基本 200% の人が基本より下がらないこと。制限のあとに 10〜300% へ丸めること。`limited` と内訳。
- `storage`: 往復、`version` 13、キーのない古いファイルは `None`、範囲外・非有限・型の不正は拒否。
- `merge`: 片側だけの変更・両側の衝突・項目名。
- 設定ダイアログ: 空欄は制限なし、プリセット、入力エラー、元に戻す・やり直し、確認の出る条件・出ない条件、`見直して適用`の完了予定。
- 回帰: 既定(制限なし)で、完了予定・換算率・見積もりが従来と一致すること。
- 全体のテストと `ty check` が通ること。実機確認はユーザーが行う。

## 含めないこと

- 乗算・平均・逓減の方式。
- 判定値の範囲(-90〜+290%)と、相対比率の丸め(10〜300%)の変更。
- タスクごと・メンバーごとの制限の指定。
- 担当候補の比較・自動の配分(必要なら別の要望)。
- 制限による影響を、ダッシュボードに出すこと。
