# タスクのパラメータ(分類)の設計(要望 51)

> **状態**: 設計(2026-10-24。レビュー待ち)— 要望 51 — `feature/task-parameters`。実装済みになったら [`CLAUDE.md`](../../../CLAUDE.md) に仕様を反映する。後続は要望 52(分解でパラメータからタスクを作る)。

## 目的

相対比率は今、メンバーごとに 1 つだけで、どのタスクでも同じ値になる(`基本比率 + 全パラメータの判定値の合計`)。ゴールは、メンバーの得意な領域のタスクを割り当てやすくすること。そこで、タスクに分類の要素として`パラメータ`を付けられるようにし、付けたタスクでは、そのパラメータについての判定値だけで担当メンバーの相対比率を決める。成功の目安は次のとおり。

- 基本 100%・Python 上級(+50%)・Java 初級(−30%)のメンバーは、Python を付けたタスクで 150%、Java を付けたタスクで 70%、付けないタスクで 120%(今のまま)になる。
- 完了予定・ダイアログの換算率・担当者向けファイルの見積もり・担当付け替え時の見直し(要望 32)が、同じ比率を使う。
- 古いファイル(version 8 以前)は、パラメータなしとして今までどおり読め、完了予定は変わらない。

## 決めたこと(2026-10-24 に確認済み)

| 項目 | 決定 |
| --- | --- |
| 付けたタスクの比率 | `基本比率 + 付けたパラメータの判定値の合計`。付けなかったパラメータは数えない |
| 付けないタスク | 今のまま(`基本比率 + 全パラメータの判定値の合計`) |
| 丸め | 今と同じ(10〜300%) |
| 付ける数 | 複数(パラメータ名の複数選択) |
| 出す場所 | 編集ダイアログの`すべて`レイアウトだけ。ガントチャートの名前の欄のチップには出さない |
| 担当の提案 | 含めない(必要なら別要望) |

## データ(`models.py`・`storage.py`・`merge.py`)

- `Task.parameters: list[str]`(既定は空)。通常タスクだけが持つ。まとめ・チェックポイントは持たない(読込で空にする)。
- 保存は`tasks[].parameters`(パラメータ名の配列)。`FORMAT_VERSION` を 8 から 9 に上げる。キーのない古いファイルは空として読み(移行は要らない)、型が不正(配列でない・文字列以外・名前の制限違反)なら読込を拒否する。重複は最初の 1 件を残して捨てる。**プロジェクトに登録されていない名前は残す**(計算では数えない。メンバーの段階の選択が、存在しないパラメータを判定値 0% として数えないのと同じ)。
- 3 者マージ: `parameters` はリスト全体を 1 項目として比べる(担当者・先行・リンクと同じ)。項目名の表(`merge.py` の日本語名)に`パラメータ`を足す。パラメータの名前変更は`id`を持たないので、削除と追加に見える(要望 51 の範囲外。既存の制約のまま)。

## 計算(`ratios.py`・`timeline.py`)

- `effective_ratio(member, parameters, only=None)` と `ratio_detail(member, parameters, only=None)` に`only: Collection[str] | None`を足す。`None` か空は今までどおり全パラメータの合計。名前のリストが渡されたときは、その名前のパラメータだけを足す(メンバーが段階を選んでいなければ判定値 0%)。丸めは今と同じ。
- `crew_of(assignees, members, parameters, only=None)`・`assignees_rate(...)` も `only` を受け取り、`conversion_rate(task, project)` は `task.parameters` が空でなければそれを渡す。空なら `None`(全合計)。完了予定の算出(`Schedule`)・ダイアログの参考値・`handoff.py` の見積もり・`reassign.py` は、すべて `conversion_rate` と `crew_of` を通るので、呼び出し元は`task`を渡すだけでよい(`crew_of` を呼ぶ箇所は、`task.parameters` を渡す形に直す)。
- ダッシュボードは割り当て率で数えて相対比率を使わないので、変更しない。

## ダイアログ(`task_dialog.py`)

- `すべて`レイアウトに、`パラメータ`の複数選択(`ui.select`・`multiple`・`use-chips`)を置く。選択肢は`project.parameters` の名前。登録されたパラメータが 0 件のときは、欄を出さない。追加・編集のどちらでも付けられる。`予定・実績`レイアウトでは隠し、値は保持する(隠した項目と同じ扱い)。
- 換算率の内訳(`task-conversion` のラベル)は、パラメータを付けたタスクでは、メンバーごとの内訳に付けたパラメータの判定値を出す。例: `換算率 150%(田中 150%×100%・Pythonを反映)→ 8h は約 0.9日分`(今の内訳の書き方に、反映したパラメータの名前を添える)。付けないタスクは今の表示。
- 比率が変わりうる編集(パラメータの付け替え)は、担当の付け替え(要望 32)と同じ条件(既存タスクで、工数があり、状態が`終了`でなく、実績か進捗度がある)で、完了予定の見直しの確認を出す。換算率が変わるかどうかの判定が、今は担当者の比較だけなので、パラメータの比較も含める。

## 周辺の挙動

- パラメータの改名は、タスクの選択に追従する。削除は、使っているタスクの件数を確認ダイアログに出し、確認後に選択を外す(`ratios.py` の`ParameterEdit`・`apply_parameter_edit`・`deletion_impacts` を、タスクも対象にするよう拡張する。メンバーとタスクの件数を別々に出す)。段階の改名・削除はタスクに関係しない。
- タスクのコピーとセクションのコピーは、`parameters` を引き継ぐ。タスクの分解は、子が元の`parameters` を引き継ぐ(引き継がないと、分解しただけで完了予定が変わるため)。「パラメータからタスクを作る」は要望 52。
- 元に戻す・やり直しの対象(タスクの編集と、パラメータの編集)。
- 担当者向けファイル(`todos.json`)と PlantUML には、独自のキーを足さない。見積もりだけが新しい換算率を使う。
- PlantUML の取り込みは、パラメータなしで作る。

## テスト

- `ratios`: 付けたものだけ・付けない・未登録名・段階未選択(0%)・丸め(上限・下限)・内訳。
- `timeline`/`handoff`/`reassign`: パラメータで完了予定・見積もり・見直しの値が変わること。付けなければ今までと同じ。
- `storage`: 往復、`version` 9、キーのない古いファイル、型の不正、重複、まとめ・チェックポイントの空。
- `merge`: 片側だけの変更・両側の衝突・項目名。
- `task_dialog`: 選択、0 件で欄なし、内訳の表示、`予定・実績`レイアウトで値を保持、見直しの確認の条件。
- パラメータの改名・削除の追従と確認ダイアログ。コピー・分解での引き継ぎ。
- 全体のテストが通ること。実機確認はユーザーが行う。

## 含めないこと

- 担当の提案(得意な人の表示)、ガントチャートのチップ、パラメータの名前変更の`id` 化、ダッシュボードの比率の反映。
