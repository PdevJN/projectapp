# チェックポイント用のタスク 設計書

作成日: 2026-10-08
ブランチ: `feature/checkpoint`(`develop` から)
経路: architectural(設計書 → 実装計画 → 実行)
要望: 作業記録の要望 21「チェックポイント用のタスク」

## 1. 目的と合意した範囲

締切の日時しかない「節目」(中間レビュー、納品日など)を、ガントチャートに載せる。登録タスクの属性として種別(通常 / チェックポイント)を持たせ、チェックポイントは、バーを持たず、大きめの ◆ だけを表示する。

合意した決定(2026-10-08):

- チェックポイントは、先行にも後続にもできる。先行にすると、その日時まで後続が押し出される。後続にすると、前のタスク群の完了が締切を超えるかを、矢印の位置で示せる。
- 状態は「未着手」「終了」の 2 つだけ。優先度・ProjectCode・色は通常と同じ。
- ◆ は、状態の色の大きめの ◆ を、締切の位置・行の中央に置く。通常タスクの締切の小さな橙の ◆ とは、色と大きさで区別する。
- 先行の完了が締切を超える見込みのとき、未着手のチェックポイントの行を赤くする(通常タスクの判定は変えない)。

やらないこと: ◆ のドラッグでの締切の移動(締切はダイアログで変える)、チェックポイントの担当・工数・実績、状態「実行中」「一時停止」、チェックポイントを担当者向けの書き出しに含めること。

## 2. データ(`models.py`・`storage.py`)

- `TaskKind(StrEnum)`: `NORMAL = "通常"`、`CHECKPOINT = "チェックポイント"`。`Task.kind: TaskKind = TaskKind.NORMAL`。
- 保存は `"kind"`。キーがない・`null` は通常。不正な値は読込を拒否する(「開けませんでした」)。
- チェックポイントの不変条件:
  - 締切(`deadline`)が必須。
  - 状態は `未着手` か `終了` のどちらか。
  - 開始予定・完了予定(`planned_start`・`planned_end`・`planned_end_manual`)・工数・担当・割り当て率・実績は持たない(空・既定値)。
- 読込: 締切がない、または状態が「実行中」「一時停止」のチェックポイントを拒否する。開始予定・工数などが入っていても拒否せず、使わない(次の保存で、空になる)。
- 保存(`forms.build_task`): チェックポイントのとき、開始予定・完了予定・工数・担当・割り当て率・実績を空にする。締切がない・状態が実行中か一時停止なら `ValueError`。
- コピー(`arrange.copy_task`): 種別を引き継ぐ(現状のコピーの規則のまま。新しい `id`、先行は空)。
- 先行タスク(`predecessors`)は、チェックポイントも持てる。

## 3. 日程の計算(`timeline.py`)

- `Schedule._resolve` は、チェックポイントについて、実効の開始と完了を、どちらも締切(`(deadline, deadline)`)にする。先行の完了で押し出さない。
- チェックポイントを先行にしたとき、先行としての完了(`Schedule.finish`)は、締切。状態が「終了」でも、実績がないので、締切を使う(実績の終了が空のため、既存の規則のとおり実効の完了に落ちる)。
- `effective_start` / `effective_end` の、先行なしの短絡(`schedule` が None で `predecessors` が空)は、チェックポイントにも、締切を返すようにする。
- `visible_range`・`counted_span` など、`Schedule` を使う箇所は、そのまま動く。`counted_span` は担当がないので、割り当てには数えない。
- `is_overdue`(`schedule` を受ける): チェックポイントで、状態が「終了」でないとき、従来の判定(現在時刻が締切を過ぎた)に加えて、`Schedule.latest_finish(task)` が締切より後なら、超過とする。通常タスクの判定は変えない。

## 4. 編集ダイアログ(`task_dialog.py`・`forms.py`)

- 上部に種別のトグル(通常 / チェックポイント)。新規は通常。
- チェックポイントのとき、開始予定・完了予定・工数・担当・割り当て率・換算の表示・実績の欄を隠す。名前・締切(必須)・先行タスク・優先度・状態(未着手 / 終了のみ)・色・ProjectCode を表示する。種別を戻すと、隠した欄の入力値が現れる(保存するまで、値は捨てない)。
- 値のある通常タスクを、チェックポイントに切り替えたとき、1 行のヒント「保存すると、開始予定・工数・担当・実績は消えます」を出す。
- 状態の選択肢: チェックポイントでは「未着手」「終了」。通常に戻すと 4 つに戻る。選択中の状態が選択肢にないとき(実行中・一時停止からの切替)は、「未着手」にする。
- 「編集中」の判定(`current()`)に、種別を含める。
- `build_task(..., kind=...)`: 2 章の保存の規則を検証する。`linkable_ids`・先行の検証は、変えない。

## 5. ガントチャートの描画(`gantt.py`)

- チェックポイントの行は、バー・進捗の塗り・割り当て超過の縞・実績の棒と点線・進捗の状態の印・締切の小さな ◆ を出さない。
- 大きめの ◆(マーカー `checkpoint-<key>-<ti>`)を、締切の位置・行の中央の高さに出す。色は状態の色(`STATUS_COLOR_VAR`。ダークテーマでは明るい色)、大きさは `CHECKPOINT_MARKER_PX`(締切の ◆ より大きい定数)。位置は締切の列の位置から、◆ の幅の半分だけ左へずらす(中心を合わせる)。表示範囲の外なら出さない(期間を指定したときの `bar_visible` に合わせる)。
- ツールチップ「チェックポイント 2026-10-12 17:00」。クリックで編集が開く。ドラッグ用の属性(`data-bar`)は付けない。
- 名前の欄: 通常どおり(優先度の背景色・ProjectCode のチップ)。担当と進捗のチップは出さない(担当も進捗度もない)。状態が「終了」なら、名前に取り消し線を引く(既存の `finished` の規則)。
- 行の赤み: `is_overdue` の結果で決める(3 章)。
- 連結の矢印: `link_bars` が、チェックポイントを `Bar(◆の中心 − 半幅, ◆の中心 + 半幅)` として扱う。
- 担当者の絞り込みでは、担当のないチェックポイントは隠れる。名前の検索には一致する。
- プレビューと PNG: 同じ描画なので、◆ も出る。

## 6. ダッシュボードと書き出し(`dashboard.py`・`handoff.py`)

- 期限とマイルストーン: 期間内の締切として一覧に出る。完了予定は締切と同じなので、既存の規則(同じ日時を 2 行にしない)で、重ならない。
- 進捗と遅れ(`summarize_progress`): 状態別の件数にはチェックポイントを含める。工数で重みづけした進捗率からは外す(工数がないので、重み 1 で入るのを防ぐ)。予定超過の一覧には、見込みの超過も出す。その行の基準の日時(`limit`)は、現在時刻が締切を過ぎていなくても、締切にする(現状の、`moment > limit` で絞った `limits` が空になり `min()` が例外になる経路を避ける)。
- 人ごとの負荷・工数の予定と実績: 担当と工数がないので、対象外(コードの変更はない。テストで確かめる)。
- 担当者向けの書き出し(`handoff.py`): 担当がないので、対象外(変更なし。テストで確かめる)。

## 7. 影響範囲

`models.py`・`storage.py`・`timeline.py`・`forms.py`・`task_dialog.py`・`gantt.py`・`dashboard.py`・`arrange.py`(コピーの確認のみ)・`docs/development.md`・`CLAUDE.md`(チェックポイントの記述)。

## 8. テスト(TDD。純粋関数を先に)

- `models`・`storage`: 往復、`kind` のない古いファイル、不正な `kind`、締切なし・状態不正の拒否、開始予定などが入ったチェックポイントの読込(使われないこと)。
- `timeline`: 実効の開始・完了が締切、押し出されない、先行にしたとき後続が押し出される、後続にしたとき先行の完了が締切を超えると `is_overdue`、終了なら超過にならない、通常タスクの `is_overdue` が変わらない、`Schedule` と単独の呼び出しが一致する。
- `forms`・ダイアログ: 種別のトグルで欄が隠れる・戻る、保存で隠した値が消える、締切なしの拒否、状態の選択肢、ヒント、編集中の判定。
- `gantt`: ◆ の位置・色・大きさ、バーなし、クリックで編集、ドラッグ属性なし、取り消し線、チップ、赤み(締切超過・見込みの超過)、矢印の端、期間の外、プレビュー、ダークテーマ。
- `dashboard`: 件数に含む・進捗率から外す、見込みの超過の一覧(例外にならない)、期限の一覧、負荷・工数・書き出しに出ない。
- 既存のテスト(1,353 件)、`ty check`、並列実行(`uv run pytest -n auto`)が通ること。
- 最後に、ネイティブで実機確認する(◆ の見た目、ライト・ダーク、全スケール、矢印、赤み、ダイアログの切り替え、PNG)。

## 9. 段階(実装計画でタスクに分ける)

1. データ(`TaskKind`・保存と検証・コピー)
2. 日程(`Schedule`・`is_overdue`)
3. ダイアログ(種別のトグル・欄の切り替え・検証)
4. ガントチャートの描画(◆・矢印・赤み)
5. ダッシュボードと文書の更新

## 10. リスクと保留

- `Task` を使う箇所のうち、開始予定・工数・担当を前提にする箇所の取りこぼし(`grep` で洗い出す。特に `gantt.py` の `task_row` と、`dashboard.py`)。
- ダイアログの欄の出し入れで、既存のレイアウト(`DateTimeFields` の列)を壊さないこと。
- 保留: ◆ のドラッグでの締切の移動、チェックポイントの完了の実績(達成した日時)、担当者向けの書き出しへの掲載。
