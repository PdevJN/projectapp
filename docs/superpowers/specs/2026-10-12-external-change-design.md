# 外部変更の検知(保存時の確認)設計書

> **状態**: 実装済み — 要望 10 の 2 — マージ PR #12(2026-10-13)。当時の記録で、現在の仕様は [`CLAUDE.md`](../../../CLAUDE.md) を正とする。

要望 5 の前提(`.claude/MEMORY.md` の「次にやること」の 5)。要望 10(git / GitHub 連携)の 2 番目の子の作業。

## 目的

別のプロセス・iCloud・git(`pull` や `checkout`)がプロジェクトファイルを書き換えたあとで、それを知らずに「上書き保存」して、相手の変更を黙って消してしまう事故を防ぐ。要望 10 では、複数人が同じリポジトリでプロジェクトファイルを共有するので、`pull` で入った他のメンバーの変更を消さないことが前提になる。

## 背景

今の保存(`storage.save_project`)は、一時ファイルへ書いてから `os.replace` で置き換えるだけで、読んだあとにファイルが変わっていても気づかない。壊れたファイルが残らない保証はあるが、相手の変更を守る保証はない。

## 範囲

**含む**:
- 読み込み時・保存時の、ファイルの内容のハッシュの記憶
- 上書き保存の直前の、外部変更の検査(`UNCHANGED`・`CHANGED`・`MISSING`)
- 外部変更があったときの 3 択の確認(上書き・名前をつけて保存・キャンセル)
- 上書きを選んだときの、相手の版の `.bak` への退避
- 「保存して開く・作成・変更」の裏の保存でも、同じ確認を挟むこと
- `CLAUDE.md` と `docs/development.md` の更新

**含まない**:
- ウィンドウに戻ったときや、一定間隔での検査(保存の直前だけ調べる)
- 「再読み込み」(自分の編集を捨てて読み直す操作)
- 自動マージ(要望 10 の 5 番目の子の作業)
- `.bak` の複数世代
- `config.json`・`holidays.json` など、設定ファイルの保護
- 新規保存と「名前をつけて保存」の検査(新しいファイルなので、相手の変更はない)

## 決定事項(確認済み)

- **外部変更を見つけたら、3 択の確認を出す**: 「上書き」「名前をつけて保存」「キャンセル」。保存の拒否だけにはしない(逃げ道がなくなる)。通知だけで上書きもしない(事故を防げない)。
- **判定は、ファイルの内容のハッシュ(SHA-256)**: 更新時刻とサイズは使わない。`git checkout` や iCloud の同期は、内容が同じでも時刻を書き換えることがあり、誤警告が出る。プロジェクトファイルは小さいので、保存のたびの読み直しの費用は問題にならない。
- **ファイルが消えていたら、通知して保存する**: 「ファイルが見つかりませんでした。新しく作成します」。相手の変更を上書きする心配がないので、確認までは要らない。
- **`.bak` は、外部変更を上書きするときだけ**: 上書きを選んだ場合に限り、上書き前のファイルを `名前.json.bak` にコピーする。1 世代で、既存の `.bak` は置き換える。普段の保存では作らない(共有リポジトリの作業ツリーに、常に変更が出るのを避ける)。`.bak` は `*.json` に一致しないので、一覧には出ない。git で除外するかは、各自の判断(`.gitignore`)に任せる。
- **調べるのは、保存の直前だけ**。

## 設計

### 検知(`storage.py`)

- `file_digest(path: Path) -> str | None`: ファイルのバイト列の SHA-256(16 進)。ファイルがなければ `None`。
- `ExternalChange`(列挙): `UNCHANGED`・`CHANGED`・`MISSING`。
- `check_external_change(path: Path, digest: str | None) -> ExternalChange`:
  - 今のファイルがなければ `MISSING`。
  - `digest` が `None`(覚えていない)なら、判定できないので `UNCHANGED`。ただし、`path` があるプロジェクトは、必ず `digest` を持つ(下記)ので、実際には起きない。
  - 今のハッシュが `digest` と同じなら `UNCHANGED`、違えば `CHANGED`。
- `backup_file(path: Path) -> Path`: `path` と同じ場所の `<名前>.json.bak` に `shutil.copy2` で退避して、退避先を返す。失敗は `OSError` のまま通す。

### ハッシュの記憶(`views.py`)

- `MainView.digest: str | None`。
- プロジェクトを開くとき(`open_project`)は、**読み込みの前に**ハッシュを取る。読み込みの間にファイルが変わっても、記憶したハッシュが古い側になり、保存時に `CHANGED` になる(厳しい側に倒れる)。
- 保存に成功したら(`write`)、書いたファイルを読み直して、ハッシュを取り直す。
- `show_project(project, None)` と新規プロジェクトでは `None`。

### 保存の流れ(`views.py` の `write`)

`write(overwrite=True)` の入口で、`self.path` があるときだけ検査する(`overwrite=False` の新規保存は検査しない)。

- `UNCHANGED`: そのまま保存する。
- `MISSING`: 「ファイルが見つかりませんでした。新しく作成します」を通知してから保存する。
- `CHANGED`: 3 択の確認ダイアログ(`forms.py` の `open_conflict_dialog`)を出し、この呼び出しは `False` を返す。
  - **上書き**: `backup_file` で退避してから保存する。退避に失敗したら、上書きせずに「バックアップを作れなかったため、保存しませんでした」を通知する。
  - **名前をつけて保存**: 名前の入力ダイアログ(`open_name_dialog`)を開き、新しいファイルに保存して、そのファイルを現在のプロジェクトにする(元のファイル(相手の版)は触らない)。
  - **キャンセル**: 何もしない。
- 確認のあとの続き(「保存して開く・作成・変更」の本体)は、保存に成功したときだけ行う。そのため、`write` と `save_then` は、続きの処理を引き継げる形にする。確認ダイアログの 3 択から保存したときも、成功すれば続きを呼ぶ。
- ダイアログの文言: 見出し「ファイルが外部で変更されています」、本文「読み込んだあとに、別のプロセスや git、同期などでファイルが変わりました。上書きすると、その変更は失われます。」

### ドキュメント

- `CLAUDE.md`: 「プロジェクトファイル」の節に、保存時の外部変更の確認(3 択・`.bak`・ファイルが消えていたとき)を足す。
- `docs/development.md`: `storage.py` の行に検知の関数を足し、実装メモに、ハッシュを読み込みの前に取る理由と、`write` の続きの引き継ぎを書く。

## テスト

- `file_digest`: 同じ内容は同じ、違う内容は違う、ファイルがなければ `None`。
- `check_external_change`: 変わっていない・内容が変わった・消えた・内容が同じで更新時刻だけが変わった(`os.utime`。`UNCHANGED`)。
- `backup_file`: 内容が同じ、既存の `.bak` を置き換える、失敗(`OSError`)。
- 保存の流れ: 通常の保存(確認なし)、外部変更ありの 3 択それぞれ(上書き: `.bak` に相手の版が残り、ファイルは自分の版になる。名前をつけて保存: 元のファイルは相手の版のまま、新しいファイルが現在のプロジェクトになる。キャンセル: 何も変わらない)、ファイルが消えているとき(通知して作られる)。
- 退避に失敗したときは、上書きしないこと。
- 「保存して開く」の経路で確認が出ること(上書きを選んだあとに続きが進む。キャンセルでは進まない)。
- 保存の成功後にハッシュが取り直され、続けて保存しても、確認が出ないこと。
- 既存のテストが、変更なしで通ること。

## 未確認・リスク

- 保存の成功後のハッシュは、書いたファイルを読み直して取る。書いてから読むまでの間に、別のプロセスが書き換えた場合、その変更は「自分が書いた内容」として記憶され、次の保存で見逃される。極めて狭い競合で、許容する。
- 外部変更の確認は、保存を押した瞬間に出る。編集の途中で相手の変更が入っていたことは、そこまで分からない(「ウィンドウに戻ったときの検査」は、あとから要望として足せる)。
- iCloud などの同期で、保存の直後にファイルが書き換わる場合、次の保存で確認が出る。誤警告ではなく、実際に内容が変わっているので、設計の範囲内。
